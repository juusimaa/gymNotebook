# UI specification — Gym Notebook

Status: proposed. Closes the "UI design — deliberately deferred" open item in [`PLAN.md`](../../PLAN.md); scope is milestones 5, 7, 8 and 9.

- **Interactive prototype:** [`prototype.html`](./prototype.html) — one self-contained file, no build step. Open it in a browser (or via GitHub Pages) and click through: sign in → cover → sessions → a session page → new page, plus progress and the exercise index off the sessions header.
- **Primary device:** phone, 390 × 844. Desktop is the same single column, centred, max-width ~430px. No separate desktop layout in this pass.

## Visual direction

Editorial paper, not skeuomorphic notebook. Serif display type (Cormorant Garamond) over a serif body (Lora) on a warm near-white ground, hairline rules instead of boxes and fills, a single gold accent used as stroke — outlined buttons, rules, the chart's line — never as a filled block. Each screen has one primary action, and it outranks everything else by weight rather than by fill: a 2px `--color-accent-700` stroke and label, 17px type, 48px tall. Secondary actions keep the hairline outline and ghost actions are text. Plain gold (`--color-accent`, 3.02:1) is decoration only — rules, hairline outlines, the chart line, the cover ornament — never a label: links, text buttons and focus rings use `--color-accent-700` (5.97:1). Secondary text (kickers, meta lines, stat labels, chart ticks, placeholders) is `--color-neutral-700` (5.83:1), and nothing is set below 11px. Numbers set tabular everywhere they stand as figures (set rows, times, weights, dates, chart axes).

Tokens live in the prototype's stylesheet as CSS custom properties: `--color-bg #f3f2f2`, `--color-text #201f1d`, `--color-accent #b68235`, `--color-divider`, `--color-error #9b3a2a` (`#d9826d` in dark mode; errors only, so a failure never shares the gold of links, focus and gains), 100–900 ramps per role, a 4.6px-step spacing scale, 2/4/7px radii and three shadow levels. The frontend lifts these into `tokens.css` and references them by variable — no hard-coded hexes in components.

**Dark mode** follows the OS setting (`prefers-color-scheme`); there is no in-app toggle. It is the same editorial page at night, not a new look: a warm ink-black ground (`--color-bg #191715`), warm off-white type (`--color-text #e1ddd8`) and the same gold, with `--color-surface` a step *lighter* than the ground. Only the colour tokens are redefined, in one `@media (prefers-color-scheme: dark)` block in `tokens.css`. Each 100–900 ramp is mirrored so a step keeps its role, not its hex, so the rules above hold unchanged: `--color-accent-700` labels (7.08:1), `--color-neutral-700` secondary text (6.19:1), plain `--color-accent` (4.81:1) decoration only. Shadows are built from `--color-shadow` (ink in light mode, black in dark), never from `--color-text`. The prototype shows the light theme only.

**Home screen.** The app can be added to a phone's home screen and then runs full-screen, without the browser's address bar: Safari's Share → Add to Home Screen on iOS, ⋮ → Install app in Chrome on Android. `public/manifest.webmanifest` gives the name, the standalone display mode and the icons. The icons are `favicon.svg` (a ruled notebook page on the ink ground: paper, a gold margin rule, three ink lines) rendered as PNGs: 180px `apple-touch-icon` for iOS, 192px and 512px for Android. The page sits inside Android's maskable safe zone, so the same 512px file also serves as the maskable icon. Full-screen means drawing under the notch and home indicator (`viewport-fit=cover`), so `body` pads itself by the safe-area insets, and full-height screens size to `--app-height` (100dvh minus those insets) rather than `100dvh`. In a browser tab the insets are 0 and nothing changes. There is no service worker: neither platform needs one to install, and an offline cache would risk serving a stale build after a deploy.

**Component-library decision (the open item in PLAN.md):** none. The screens need inputs, buttons, tags, lists and one chart; the whole surface is small enough that hand-written CSS against the tokens is less work than restyling a library out of its own look. The chart is hand-drawn SVG (see Progress) and did not change this.

## Screens

### 1. Login — `/login`
One route with three modes and two result states, switched in place rather than as separate pages, so the browser's back button leaves the screen instead of stepping through them (specs/002 contracts/ui.md).
- **Sign in:** Email, Password, "Forgot your password?" (a text button right under the password), "Sign in". Below the form: "New here? Create an account". Backs onto `POST /auth/login`. A 401 ("Email or password is wrong") returns here with the address kept, the password cleared and focus back in it. A 403 `email_not_verified` (right password, address not confirmed) is not an error line: it switches to **Check your inbox**. Arriving from a confirmation link fills the address in.
- **Create account:** Email, Password (`new-password`), "Name on the cover" (`nickname`, at most 50 characters), the Turnstile bot check, "Create account", and "Already have an account? Sign in". A short service description sits immediately before the action's end of the form: the free training log, provider, core records, and why the email and password are asked for. It describes what registration requests; it is not notice acknowledgement or consent. Backs onto `POST /auth/register`, which answers every valid signup the same way, so it always goes on to **Check your inbox**.
- **Forgot password:** Email, the Turnstile bot check and "Send link", then "Remembered it? Sign in". Backs onto `POST /auth/password-reset`, which answers every address the same way, so it always goes on to **Reset sent**. Opened from `/reset-password` with a dead link, it starts here with a line saying why ("That reset link has expired…" / "…no longer works…").
- **Turnstile bot check** (Create account and Forgot only, and only when a site key is configured; specs/002 contracts/ui.md): Cloudflare's widget between the last field and the button, drawn by Cloudflare's script in an iframe, `theme: auto` so it follows the OS colour scheme like the rest of the app. "Flexible" size (full width, 300px minimum) where the column is at least 300px wide; on narrower phones (a 320px screen leaves about 265px) the compact widget instead. The submit button stays disabled until the widget has a token, and every attempt resets it for a fresh one. A refused token reads "The check didn't pass. Try again." If Cloudflare's script can't load: "The bot check couldn't load. Check your connection and try again." Without a site key nothing is shown and nothing is loaded from Cloudflare.
- **Reset sent:** "Check your inbox" — "If there's an account for *address*, we've sent a link to choose a new password. It works for one hour." — and "Back to sign in". Focus moves to its heading.
- **Check your inbox:** names the address, says the link lasts 48 hours, "Send the link again" (`POST /auth/verification` with the email and password still held in the screen's memory; leaving the screen drops the password), "Back to sign in". Focus moves to its heading when it appears.

Email fields are `type="email"`, `inputmode="email"`, `autocomplete="username"`, with auto-capitalisation, auto-correct and spell-check off. Rate-limit rejections (429) show an inline message under the button, not a toast.

### 1a. Confirm email — `/verify-email#token=…`
Public: the link often opens in a mail app's own browser, or in Safari while the app lives on the home screen, so it never needs a session. Reads the token from the URL fragment once, removes it from the address bar, and posts it to `POST /auth/verify-email` from script (a mail scanner that opens links without running script confirms nothing). "Confirming…", then one of:
- **Address confirmed:** "*address* is confirmed." and **Sign in**, which opens `/login` with the address filled in, or **Open my notebook** when this browser already has a session.
- **This link has expired** (48 hours): a way to sign in, where the unconfirmed sign-in offers a fresh link.
- **This link doesn't work** (tampered, cut short, or no token): "Go to sign in".
- **Couldn't confirm yet** (offline, 429, server error): the reason and **Try again**, with the token still held in memory.

### 1b. Reset password — `/reset-password#token=…`
Public, for the same reason as 1a; also where the "finish creating your account" email leads. Reads the token from the URL fragment once and removes it from the address bar, but posts nothing until the form is submitted, so a mail scanner opening the link changes nothing.
- **Form:** New password and Repeat new password (both `new-password`), "Set password", and a muted line: "This signs you in here and out everywhere else, including the app on your home screen." Different passwords are caught on the screen, before a request. Backs onto `POST /auth/password-reset/confirm`; on success the returned token is stored and the screen goes to `/` (replacing itself in history), through the usual guards. A password the server refuses, a 403 `account_suspended` (the existing suspension copy), a 429 or a 503 show as an inline line under the form.
- **This link no longer works** (expired, already used, tampered, or no token): one sentence on why ("Reset links work for one hour." / "Each reset link works once.") and **Send a new link**, which opens `/login` in Forgot password mode with the reason shown.

### 2. Cover — `/`
The page you land on after login; the owner name comes from `displayName` on `GET /auth/me`. Volume, year, one "Open the notebook" primary action, then "Signed in as *address*" in small muted type (it may wrap anywhere, so a long address never widens the page) and "Sign out" below it as text. Deliberately carries no other data — it is the closed cover of the book, and its job is to make opening the log a decision rather than a dashboard. Sign-out drops the token client-side.

### 3. Sessions — `/workouts`
`GET /workouts?limit=&before=`, newest first, flat — **no date grouping**. Each row: day + month numeral on the left (the day in Lora, like every figure — Cormorant's tabular "11" reads as a Roman "II"), title, start time, an exercise-name summary and a meta line (`3 exercises · 9 sets · 07.15–08.40`; when the end falls on a later day than the start, its date follows, `23.30–00.15 16 Sep`, so a page finished days late can't pass for a short session — the session page's time range does the same) — all of it from `exerciseNames`, `exerciseCount`, `setCount` and `endedAt` on the row, so the list is one request. Two sessions on one date are two adjacent rows distinguished only by their times; the prototype's sample data contains such a pair (8 Sep) and it must survive any list refactor. A row without `endedAt` reads "in progress" where a finished row shows its start time, its meta line ends "from 19.34" instead of repeating the start, and a secondary **Continue logging** button under it, aligned with the title, opens `/workouts/{id}/edit` — beside the row link, never inside it. Header links to Progress, Exercises and the cover; sticky primary action at the bottom: "Start a new page".

### 4. Session page — `/workouts/{id}`
`GET /workouts/{id}`. Heading block: long date kicker, title, then start–end, bodyweight and gym on one meta line; absent optional fields degrade to plain text ("bodyweight not logged"), never to an empty slot. Then one block per `WorkoutExercise` in `position` order, each with its computed best on the right — `e1RM 99 kg`, or `best 8 reps` when the block's `isBodyweight` is set. Set rows are `n / load`, plus a "warm-up" tag on warm-ups only: a working set is the default and carries no tag. Warm-up sets are set in `--color-neutral-700` and are excluded from the best figure. Notes justified at the bottom. With the privacy feature on and no optional-details consent, the title falls back to "Untitled session", the meta line shows only the times, and the notes block is hidden (user story 6, below).

Edit and Delete sit in the header. While the session is in progress (no `endedAt`) the page's primary action is **Continue logging**, at the bottom of the page and opening the editor, and the header shows only Delete, so there is one way in, not two. Delete opens an inline confirm in place ("Tear out this page? Its 3 exercises and 11 sets go with it.", counted from the page; focus moves to **Keep**, and Keep returns it to Delete) rather than a modal — it names the cascade, since that is what `DELETE /workouts/{id}` does.

### 5. New page — `/workouts/new`
Exercises first. The page heading folds into one dateline under the header — "Today 09.34 · add details" (the title in place of "add details" once there is one; "3 Oct 07.15–08.20 · edit details" on the edit page) — a single 44px button that opens the fields in place: date beside started, then title, bodyweight beside gym, and notes; the edit page adds finished. A save that fails on one of those fields opens it again, so the message never points at a hidden field. Every field-level failure — heading or set — marks the field with `aria-invalid`, ties it to the footer message with `aria-describedby`, and moves focus there; editing the field clears both the mark and the message. With the privacy feature on and no optional-details consent, title, bodyweight, gym and notes are replaced inside it by one **Add title, location, notes and bodyweight** entry (user story 6, below). Exercise blocks are separated by hairline rules, not cards. Each block: name, a kg/bodyweight marker, on a new page — and on the edit page of a session still in progress — a "last time 100 kg × 5" line from the picked suggestion's `lastSet` (blocks already on an in-progress page get theirs from one `GET /exercises?search=&excludeWorkoutId=` when the page opens, so Save page then Continue logging keeps the reference) (it ends "· warm-up" when the latest session logged only warm-ups for the exercise, wherever `lastSet` is printed); the edit page searches with `excludeWorkoutId` so "last time" is the session before, never the page's own sets, and a finished page being corrected shows none, since its "last time" could be a later session, one column header (WEIGHT / REPS, or LOAD / ADDED KG for bodyweight), and set rows of `weight / reps / Warm-up / ×`; a bodyweight block hides the weight field unless added weight is enabled. "Add set" is the ditto mark, drawn as a full-width 48px dashed row under the sets (a blank line waiting to be written on, the block's next action rather than a corner link): the new row repeats the figures above (weight and reps) but always starts as a working set, so the first heavy set after the warm-ups can't be logged as a warm-up by accident and drop out of progress; each further warm-up is pressed as such. It takes focus on its weight (reps for a bodyweight block) with the figure selected, so a repeated set is one tap. Tapping a weight or reps field selects its figure the same way, so a different number is typed straight over the copied one; a second tap places the caret for editing a single digit. The toggle is always named "Warm-up" (13px, a hairline outline so a column of them stays quiet), with `aria-pressed` for its state; pressed it is a tag filled with `--color-neutral-300`, which stays visible on the dark ground, and the row's figures recede. The × is a 44px target, set 4px apart from the toggle. Removing a set or a whole block leaves "Removed set 2 · 100 kg × 5. **Undo**" (or "Removed Back Squat and its 3 sets.") in its place, with focus on Undo. There is no timer: the offer lasts until the next edit in that block (for a block, until the next removal or added exercise), and only the latest removal can be undone. `setNumber` is never sent — the server assigns it. Below the blocks, an autocomplete field backed by `GET /exercises?search=` whose suggestions show `lastSet`; it searches once typing pauses for 250 ms and keeps the previous answer on screen while the next search runs, so the picker doesn't jump on every keystroke (the add-as buttons wait until the answer covers exactly what is typed); picking one appends a block and moves focus straight to its first set's weight (reps for a bodyweight block). A block picked with a `lastSet` starts with that set written in — weight, reps and warm-up flag, the ditto mark across sessions — unless last time opened with a warm-up (`firstSet.isWarmup`): then it starts with that warm-up, so the session opens the way the last one did; "Add set" repeats its figures as a working set. Either way the figure is selected, so the same set as last time costs no typing and a different one is typed over it; a bodyweight `lastSet` with added weight opens with the weight field showing. Enter moves forward, since a phone's numeric keypad has no Tab: weight (`enterkeyhint="next"`) → reps → the next set's first field; on a block's last set reps says "done" and Enter closes the keyboard rather than adding a set, so a stray Enter can't log a set nobody did. While the field has focus, its suggestions scroll into view above the sticky footer, and focusing it scrolls the field itself into view once the keyboard is up; the editor is sized to the visual viewport so the keyboard shrinks it (iOS Brave and Firefox scroll the whole page instead). Existing matches are listed first and the add-as choice last, so a near-miss offers the existing name before inviting a typo'd duplicate. When no exact name matches, the user adds the typed name as either Loaded (kg) or Bodyweight — "Not in the list? Add **Taka** as a new exercise:" under matches, "No exercise called **Taka** yet. Add it as:" when there are none; the bulk save creates it and a follow-up `PATCH /exercises/{id}` persists a new bodyweight choice. The whole exercise list commits with one `PUT /workouts/{id}/exercises`. "Save page" leaves the session in progress; "Finish session" is the primary action on a new page (the edit page's is "Save changes") and first opens an inline confirmation with a distinct "Confirm finish" button, and confirming writes `ended_at`. The confirmation saves the current time only when the page started within the last 6 hours; a page started earlier (a session never closed out, then continued on another day) or ahead of the clock instead asks "This page started 30 Sep 07.15. When did the session finish?" with a required time field, which takes focus, and Confirm finish saves that time on the page's own date (a time earlier than the start rolls to the next day, as the edit page's Finished field does). The confirmation replaces the footer's Save/Finish buttons while it is open (focus moves to "Keep editing" and returns to "Finish session" if cancelled), so the footer never shows two rows of buttons at once. An edit page whose session is still in progress (reached by **Continue logging**) behaves like a new page: Finish session is its primary and Save changes the secondary.

**Draft safety.** The editor keeps a copy of its draft in this tab's `sessionStorage` (`frontend/src/screens/editorDraftStorage.ts`), one key per route: the new page, and each workout's edit page. So a reload, a locked phone or a discarded tab doesn't lose a half-logged session. The copy is written only while the draft differs from where it started (a fresh page, or the saved workout). It holds the four optional details only while the account allows them.
- **Restore.** Opening the route again restores the copy, ahead of a fresh page or the server's copy, under a quiet note: "Restored your unsaved page from 09.42." (the date too when it's from another day). Its **Start over** (new page) or **Discard changes** (edit) asks first, like Cancel. A new page whose heading was already saved keeps that workout's id, so a retry after a reload updates it rather than creating a second page.
- **Cancel.** An unchanged draft leaves silently. A changed one asks inline, in the same band under the header as "Tear out this page?": "Discard this page and its 11 sets?", or "Discard this page?" with no sets, or on the edit page "Discard your changes? The page stays as it was last saved." A new page whose heading already reached the server adds "The part already saved stays in your notebook." **Keep editing** takes focus, and **Discard** removes the copy and leaves. No browser `confirm()`.
- **Cleared** on a successful save, on Discard, on sign-out, on account deletion, when another tab signs out, and on any other 401. A tab that starts without a token clears what it holds, which covers a sign-out it missed while discarded. Withdrawing consent strips the four details from every stored copy.
- **Expired token.** Tokens live 30 minutes with no refresh, so a long session's save can meet a 401. When the token's own `exp` has passed, the copy is *held* rather than cleared. It survives the trip to sign-in, and a reload there, and comes back when the same user signs in again. Signing in as another account removes it.

### 6. Progress — `/progress`
`GET /exercises/{id}/history?from=&to=`. Header links to Sessions and Exercises. A horizontally scrolling exercise picker (selected one carries the accent stroke; each edge fades while there is more to scroll that way, so a clipped name says the row goes on), then the exercise name and a metric line that states what is plotted and in what unit — **"Best e1RM per session · kg"** (the line is set in capitals, but "e1RM" keeps its own case), or **"Best reps per session · reps"** for a bodyweight exercise. The y-axis label changes with it; nothing else about the screen does.

The chart is hand-drawn SVG: hairline gridlines at each y-tick, one accent polyline, hollow points, and HTML axis labels positioned over it (labels are HTML, not `<text>`, deliberately — see Implementation notes). The y-range is the data's own range plus ~12%, snapped outwards to a round step (1, 2 or 5 × 10ⁿ, never under one kg or rep) chosen for about three intervals, so ticks read 58 / 59 / 60 rather than 57.5 / 58.8 / 60, and a plateau reads as a plateau instead of being flattened by a zero baseline. The x-axis labels the first and last dates; when they are the same day it prints that date once, centred.

Under the chart, Latest / Best / Change figures (set in Lora), each with its unit beside it ("99 kg", "+5 kg", "12 reps"); a change is the difference between the printed figures, not the precise estimates behind them, so 94 → 99 reads +5, never +5.5, and a lift with one session shows "—" and "one session so far" rather than a change since itself. Then one row per session — date, the set it came from, the figure, and the change from the session before, with gains in `--color-accent-700`. Newest first, matching the sessions list.

Three things the screen must say out loud, because they are the plan's e1RM rules made visible:

- A tested single charts as the weight itself, and its row is annotated as a tested single — never an Epley-inflated estimate.
- A bodyweight exercise charts reps, and a line under the chart says so and that belt-loaded sets are not charted here.
- For loaded exercises that line instead warns that estimates degrade above roughly 12 reps.

Two sessions on one date are two points, not one — the Pull-up series in the prototype has such a pair (8 Sep morning and evening).

### 7. Exercise index — `/exercises`
`GET /exercises?search=`: a search field, then every exercise with its session count, `lastSet` and a kg/bodyweight marker. One line of prose explains that exercises come into being by being used — there is no "add exercise" action anywhere, and the absence needs accounting for. The prototype's list deliberately contains a typo'd "Bnech Press" so the merge case is demonstrable.

### 8. Edit exercise — `/exercises/{id}`
`PATCH /exercises/{id}`, and the escape hatch for names typed wrong. Shows the name as logged with its history count, then:

- **Name** — a text field, with a note that casing and spacing are the user's to keep ("Back Squat" and "back squat" are the same exercise underneath), which is `normalized_name` explained without naming it.
- **Merge** — when the typed name normalizes onto another existing exercise, an accent-stroked notice appears and the primary action becomes "Merge into <name>". It states how many sessions move, that the old name disappears from the index, that nothing is deleted, and that it can't be undone from here. The merge is not a separate screen or a second confirm: it is the same rename, and the server treats it as one.
- **Load** — a switch between "Loaded (kg)" and "Bodyweight", each with its consequence spelled out (reps vs e1RM; weight means *added* weight). This is the read/write surface for `is_bodyweight`.
- **Save** — disabled until the name or the load differs from the exercise as loaded. It reads "Save name", "Save changes" once the load has changed, or "Merge into <name>".
- **Remove** — explained, not offered. An exercise with sets against it can't be deleted; the copy says so and points at renaming-onto as the fix.

### Privacy and account lifecycle

Screens for `specs/001-privacy-account-lifecycle/spec.md`. The notice screens (user story 1), the export (user story 3), account deletion (user story 4) and optional-details consent (user story 6) are implemented behind `PRIVACY_LIFECYCLE_ENABLED`. The frontend has no flag of its own: when the privacy routes return 404, the links below are hidden and the gate is skipped.

**Implemented (user stories 1, 3, 4 and 6):**

- **Public notice, `/privacy`.** A "Privacy notice" link sits under the sign-in form, shown only when the API serves a notice. The screen shows the version and effective date, what changed in this version, and the notice's sections as plain text. It also shows any announced future version in a box with its effective date, summary and expandable full text. It works signed out, and reading it records nothing. "← Back" returns to sign-in, or to Privacy & account when signed in. Focus moves to the heading on load. A link to a section, such as `/privacy#notice-contact`, scrolls to it instead.
- **Privacy & account, `/account/privacy`.** A "Privacy & account" link on the cover, on its own line below Change password and Sign out, shown only when the feature is on. The screen states whether the current notice version has been continued past, and when. It notes that continuing is not consent, and links to the notice, to the export, to account deletion (**Delete my account**) and to the notice's contact section. It is reachable without acknowledging the notice.
- **Notice gate, `/account/privacy/notice?returnTo=…`.** Shown before any notebook screen, whether reached through "Open the notebook" or a deep link to workouts, progress, exercises or an editor, when the account hasn't continued past the current version. The screen has:
  - the full notice;
  - a sticky footer: "Continue records the version shown to you. It does not record consent." plus **Continue to notebook**;
  - Back to the cover, Privacy & account and Sign out, none of which record anything.

  Behaviour:
  - Continue sends exactly the version on screen and, on success, opens the page the user was heading for. Only same-origin notebook paths are honoured; anything else opens the sessions list.
  - If a newer version took effect meanwhile, the gate loads it and says so. A network or server failure keeps the gate, with an inline message and the button available to retry.
  - There is no checkbox and no "I agree".
- **Export, `/account/export`.** "Take a copy", reached from Privacy & account's **Export my data**. It explains that one JSON file holds the account details, exercises, sessions, notes and sets with explanations of every field, and warns that the file is personal. The user enters the current password and chooses **Download my data**.
  - **States:** idle; "Checking your password…" while the password is verified; "Preparing your file…" with an indeterminate progress bar while the file arrives, with **Cancel**; and complete, "Your file has been saved as gym-notebook-export.json. Your notebook has not changed.", with **Download again**. The status line is a polite live region.
  - **The password field is cleared** as soon as the request is sent and is never stored, so every attempt, including a retry, asks for it again and gets a fresh snapshot.
  - **Only a complete file is saved.** A cut-short or cancelled download saves nothing. The file is held in a temporary object URL that is revoked shortly after the save starts, or at once when the screen is left.
  - **Errors** stay on the form (`role="alert"`) and return focus to the password field: a wrong password; too many attempts; an export already running; the notebook briefly busy (503); and anything else, "The export didn't finish, so no file was saved. Your notebook has not changed. Try again." A 401 means the session no longer works, so it signs out to the login screen.
- **Delete your account, `/account/delete`.** Two steps, so the irreversible action is never one tap from the explanation.
  - **Review** ("Before you leave"): what is removed (account, exercises, sessions, notes, sets and the notice record), that every signed-in session loses access, and that it can't be undone. **Export first (optional)** links to the export; it is never required. "What remains for a limited time" names backup copies (up to 30 calendar days), the minimal deletion record in the service logs (a random account identifier and the time, up to 31 days, so a restore can't bring the account back) and the restricted security-log exception (each log expires 30 days after it was collected). **Continue to delete** or **Keep my account**.
  - **Confirm** ("Confirm with your password"): focus moves to the heading. The current password and **Delete my account permanently**. The password is cleared once sent. While the request runs, the button is disabled and the status line says "Deleting your account… Closing this page won't stop it." There is no Cancel at that point, because the server finishes a deletion it has started.
  - **Failures that deleted nothing** stay on the form (`role="alert"`, focus back to the password): a wrong password, too many attempts, the account briefly busy (503 `temporarily_unavailable`), or the feature switched off. Each says nothing was deleted, so retrying is safe.
  - **Failures with an unknown outcome** replace the form with an explanation that claims neither result:
    - "We couldn't confirm the deletion", for 503 `deletion_outcome_unknown`, a broken connection or an unexpected status. It offers **Check my account** (the cover, whose guard shows whether the session still works) and **Privacy contact**.
    - "Your session has ended", for a 401. It says the 401 doesn't show whether the account was deleted, signs this browser out, and offers **Sign in again** and **Privacy contact**.
- **Account deleted, `/account/deleted`.** Public, since there is no account left to sign in to. After a successful deletion this browser is signed out (other tabs follow) and this screen shows "Your account is deleted", with the dates the server returned: when backup copies expire, when the deletion record expires, the restricted-log sentence, and a note that downloaded files stay on the device. **Return to sign in**. It renders the deletion only from the state the deletion screen hands over: typing the address, or reloading into it from anywhere else, shows a neutral "You're signed out" and claims nothing.
- **Optional workout details, `/account/privacy/optional-details`.** A workout's title, location, notes and bodyweight are stored only with consent, because they can reveal health information (user story 6). The screen shows the versioned consent statement as plain text, with **Allow** and **Not now** side by side in the same style; nothing is preselected. Allow sends exactly the version on screen; if the statement changed meanwhile, the newer one loads and nothing is recorded. Not now records nothing and returns to Privacy & account.
  - **With consent**, the screen shows when it was given and **Withdraw**.
  - **Withdraw** opens a review first: every workout's four details are permanently removed, the rest of the notebook stays, the details can be allowed again later with empty fields, and an export link is offered. **Remove details** or **Cancel**; no password. Success says how many workouts were cleared ("No optional details were left to remove." on a retry). A failure keeps the review with a retry, which is safe.
  - **Privacy & account** gets an "Optional workout details" block. It states the consent, or that the fields are hidden, or that a transition question is pending. It links to **Review and allow**, **Choose now**, or **Withdraw**, which opens the review directly, so withdrawing takes no more steps than allowing.
  - **Editor.** Without consent the four inputs are hidden, and one **Add title, location, notes and bodyweight** button takes their place. It opens the same statement and choice *inline*, so the draft is kept; Allow reveals the fields and focuses Title, Not now returns focus to the button. The session page hides the same fields. While the check is loading, or if it fails, the fields stay hidden.
  - **Rejected save.** A 403 `optional_details_consent_required`, for example from a tab left open after withdrawing elsewhere, keeps the draft, removes only its details, explains that they weren't saved, and shows the opt-in entry again. It never signs out.
  - **Transition question.** An account that already holds details without consent is asked after the notice gate, before any notebook fetch. It sees "Keep your optional details?" with the number of affected workouts, an export link, the statement, and **Allow** and **Don't allow** of equal prominence. Don't allow goes through the withdrawal review, then **Continue to notebook**. Leaving via Back to the cover, Privacy & account or Sign out answers nothing, so the question returns on the next visit. Accounts without details are never prompted.
- **Session invalidation, everywhere.** When the session ends, the app clears the token, cancels requests in flight, releases any export file waiting to be saved, and opens sign-in, which also drops every open notebook screen and editor draft. The one exception is a plain token expiry: the stored editor draft is held for the same user's next sign-in (New page → Draft safety). This applies to any request that answers 401 (except change-password's wrong current password and deletion's own 401), to another tab signing out or deleting the account, and to a page restored from the back/forward cache, which reloads so the guards run before anything personal shows. A 400 wrong password on export or deletion stays with the form. If the 401 came from a save, sign-in shows "You were signed out while a change was being saved. It may already have been saved, so check your notebook before entering it again." until the user signs in (research R4, Q5).
- **Every state:** loading ("Opening the notice…"), a load failure with **Try again**, and a "not available" state for when the feature is off. Errors use `role="alert"`, all controls are at least 44px, and focus moves to each screen's heading once it loads. That heading is the screen's `h1` (drawn at 32px, the size of the other reading titles), its sections are `h2`, and every date is written in the interface's English ("4 October 2026") whatever the browser's locale. The notice's version identifier is shown as the server sends it.

**Design preview only (prototype):**

- **Export:** The same screen as the implemented one, but it downloads a *sample* file in the real format (version 1) instead of reading an account. An empty password or the literal `wrong` shows the inline verification error; a prototype link shows the recoverable failure.
- **Deletion:** The same two steps as the implemented screens: a review naming what is removed, the optional export, the 30-day backup limit, the 31-day deletion record and the restricted security-log exception, then a separate password step. An empty password or `wrong` shows an inline error; a prototype link shows a recoverable failure. Success leads to a completion screen explaining backup, deletion-record and log expiry. No real account is deleted.
- **Optional details:** the editor's opt-in entry, the consent screen, withdrawal with its review, and a prototype control on the account privacy screen that previews the transition question. Consent lives in memory, and withdrawing changes no sample data.
- The prototype keeps acknowledgement in memory and has a control on the account privacy screen for previewing a revised notice version; reloading resets all demo state. Controller details, legal bases, processor/transfer information, contact details and provider retention settings remain review gates in the feature specification — neither the prototype nor the synthetic development notice is a publishable notice.

## Rules the UI must not break

These are UI-visible consequences of decisions in PLAN.md; each one is a thing a redesign can quietly undo.

1. A page is a session, not a day — never group or merge rows by date, in the list or on the chart.
2. Warm-up sets are visually demoted and excluded from the progress figure.
3. Bodyweight exercises show reps, not kg; added weight shows as `+10 kg × 5`.
4. `reps == 1` shows the weight itself, not an Epley estimate, and says that it is a tested single.
5. The chart always states its metric and unit; the y-axis label follows the exercise's `isBodyweight`.
6. kg only, one decimal for bodyweight, 1.25 kg steps for plates.
7. Optional heading fields are genuinely optional and read as prose when absent.
8. Destructive actions name what they destroy: a page delete says the sets go with it, a merge says how many sessions move.
9. There is no "create exercise" action — names arrive by being typed into autocomplete.
10. Hit targets ≥ 44px — this is used standing at a rack, one-handed. That includes text links in a header (`.header-link`), not just buttons.
11. Times use Finland's 24-hour `HH.mm` convention (`07.15`), even though the interface language is English.
12. Text meets 4.5:1 on its ground, and no text is smaller than 11px. Gold (`--color-accent`) never carries text; muted text is `--color-neutral-700`, not 600 or 500. Error lines and invalid fields use `--color-error` and nothing else does; an invalid field also doubles its border weight, so it differs from a focused one without relying on colour. A message that isn't a failure ("Sent again", "Page saved") is set in ink.

## Implementation notes

- **Arrival notices.** A save, merge or delete that changes screens says so on the screen it lands on, in one ruled line under the header (a polite `role="status"`): "Page saved. It stays open for more sets." or "Session finished and saved." on Sessions, "Changes saved." on the session page, "Renamed to Bench Press." or "Merged into Bench Press." on the exercise index, "Page torn out." after a delete. It travels in router state, never the URL, and shows once: a reload or a later Back doesn't repeat it.
- **Chart axis labels are HTML, not SVG `<text>`.** They sit absolutely positioned over the chart box (y ticks) and in a flex row beneath it (first/last date). This keeps the labels in the same type system as the rest of the page and out of SVG's text metrics; the drawn SVG is only gridlines, the polyline and the points.
- The chart's plot area leaves a 38px left gutter for the y labels; both the SVG and the label column are positioned against it.
- `is_bodyweight` is read from the block (`GET /workouts/{id}`) and from the autocomplete result (`GET /exercises`), and written only here.

## Still open

- Empty states (no sessions yet, no exercises to search, an exercise with one session and so no chart to draw) and error/offline states are not drawn.
- Date range filtering on the progress view: the endpoint takes `from`/`to`, the screen currently plots everything.

## How this lives in the repo

```
docs/
└── ui/
    ├── README.md       # this spec
    └── prototype.html  # self-contained clickable prototype
```

Committed on a branch via PR like any other change. The prototype is a reference artifact, not a build input — nothing under `frontend/` imports it. When a screen's design changes, update the prototype and this file in the same PR that changes the code, so the spec can't drift silently. Serving `docs/` with GitHub Pages gives the prototype a shareable URL; linking it from `README.md` and from PLAN.md's frontend section is what makes it discoverable.
