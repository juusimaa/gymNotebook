# Rights-request procedure

Owner/reviewer: Jouni Uusimaa, Gym Notebook controller. Version: draft 2026-09-28. Privacy contact: **jouni.uu@proton.me**, as recorded in [processing-decision.md](processing-decision.md). This procedure implements FR-025 and [the operations contract](../../specs/001-privacy-account-lifecycle/contracts/operations.md#rights-handling). The owner must test that the address is monitored and practise the cases in T083 before the feature is released. Do not put real requests, replies, account IDs or evidence files in Git.

The legal starting points are [GDPR Articles 12–22](https://eur-lex.europa.eu/eli/reg/2016/679/oj/eng) and the [EDPB's small-business rights guide](https://www.edpb.europa.eu/sme/be-compliant/respect-individuals-rights_en). The process below is an operating decision, not an automatic approval/refusal rule for every request. Apply the person's actual right, the processing purpose and any lawful exception to the facts.

## Intake, register and deadline

1. Check the Proton privacy mailbox on every working day, including while away; the owner confirmed on 2026-09-28 that they will do this personally. If that becomes impossible, arrange coverage before the absence and review any new recipient or access arrangement in [suppliers.md](suppliers.md). Accept a request even if it does not use a legal label or the preferred channel; note the earliest date/time it reached the controller. A self-service export or deletion does not prevent someone asking for broader access or help after losing sign-in. Acknowledge receipt and state the expected response date without asking for a password by email.
2. Move correspondence to a restricted Proton Mail folder for rights requests. In the FileVault-encrypted operator-only local register, with cloud sync disabled, record only: opaque request reference, request type(s), UTC receipt, contact channel, identity-check outcome (not identity-document copies), original deadline, any extension notice/date/reason, action and response date, closure date, absolute disposal date and restricted evidence reference. Keep account identifiers and request contents in the restricted case material only where necessary. Confirm local backup/sync behavior before the first real case.
3. Set an internal deadline **one calendar month from receipt** and respond without undue delay. Do not substitute a 30-day timer. For a date absent next month, use that month's last day: a request received 31 January is targeted for 28 February, or 29 February in a leap year. Set a working reminder earlier, including when the date falls on a weekend/holiday. Identity questions do not silently restart the original clock. The [EDPB guide](https://www.edpb.europa.eu/sme/be-compliant/respect-individuals-rights_en) explains the one-month response and, for complexity or number of requests, a possible two-month extension if the person is told within the original month with reasons.
4. If an extension is genuinely needed, record why, notify the person by the original one-month date, and set the revised calendar-month deadline. If no action will be taken, explain the specific reason within the original month and the possibility of complaining to the Finnish Data Protection Ombudsman and seeking a judicial remedy. Do not charge or refuse merely because the request is inconvenient or repeated; the GDPR's manifestly unfounded/excessive test needs a recorded case-specific basis.

## Verify only what the request needs

Use the existing signed-in route and current-password verification where it answers the request. The account has no verified email field, so the sender of an email is **not** authenticated merely by knowing a username or writing from the Proton contact thread. For an unauthenticated request, ask only for information necessary to resolve reasonable doubt and select a secure verification route appropriate to the information to be disclosed or changed. Never request the account password, JWT, invite code or a full identity document by ordinary email. Do not automatically collect identification documents. If identity cannot be established, explain the problem and work on a proportionate method while tracking the original deadline; do not disclose another person's notebook or silently close the request. The [EDPB guide](https://www.edpb.europa.eu/sme/be-compliant/respect-individuals-rights_en) allows additional identity information where there are reasonable doubts.

The exact manual verification path for someone unable to sign in needs a practice case in T083. If it cannot be demonstrated without excessive collection or unsafe disclosure, record the gap as a release blocker and improve the procedure before publication.

## Handle each requested right

| Request | Operator action and decision record |
| --- | --- |
| Access | Search the live account/notebook, notice/consent record and relevant restricted logs or correspondence. The self-service JSON file is one route, not the limit of an Article 15 request. Review security material for safe disclosure rather than automatically denying it. Provide the required explanation, recipients, retention and available copy without another user's information or secrets. |
| Rectification | Verify the disputed item, correct inaccurate data or explain why no change is appropriate. The user can edit notebook entries directly when signed in. Record any recipient notification that is required and feasible. |
| Erasure | Offer self-service deletion if usable. For a broader or post-lockout request, verify identity, evaluate the requested scope and any lawful limits, then apply the documented deletion/restore protocol. Do not claim backup or log disposal before evidence supports it. |
| Restriction | Identify the relevant processing and whether restriction grounds apply. Record the practical control used and notify the person before lifting a restriction where required. If the current application cannot enforce the needed restriction, keep the affected processing closed and resolve the gap; do not claim an unsupported feature. |
| Objection | Identify the purpose and lawful basis. Assess an objection to legitimate-interest processing on its facts; stop it unless a documented applicable ground permits continuation. Do not treat a consent withdrawal as an objection or vice versa. |
| Portability | Assess whether the requested data meet Article 20's conditions. The self-service JSON export can help, but review scope and transmission method for a broader request. Explain any information outside portability while separately addressing access rights. |
| Complaint / explanation | Give the Finnish Data Protection Ombudsman's route and explain the action taken, any refusal or extension, and judicial remedy information where required. Do not require a complaint to come through Gym Notebook first. |

Where personal information was disclosed to recipients and a correction, erasure or restriction notice is required, assess Article 19 and document the result. Protect other people named in free text. For a suspected breach or dispute, use a separate incident record with limited access; do not turn a rights request into an indefinite general archive.

## Close and dispose of the case (Q8)

The owner approved this operating choice on **2026-09-28**: keep routine correspondence in the restricted Proton Mail folder and the minimal register in a FileVault-encrypted local file with cloud sync disabled. Delete both **no later than 12 calendar months after case closure**. Set the absolute disposal date when closing, review it regularly and record disposal in the register before removing its personal case row; retain only non-identifying aggregate counts if useful. If the mailbox's trash, provider backups or local backups cannot meet the chosen maximum, resolve that before real requests are collected there; [suppliers.md](suppliers.md) and T076 track the provider evidence.

A longer hold is possible only for a specific reviewed legal obligation or concrete dispute/claim. Before extending, record the precise material, purpose/basis, owner, access limit, review date and end condition in restricted evidence, and tell the person where the law requires it. This is not an indefinite default. The [EDPB's access-rights review](https://www.edpb.europa.eu/system/files/2025-01/edpb_cef-report-2024_20250116_rightofaccess_en.pdf) notes that the GDPR sets no single retention period for request correspondence and calls for documented, objective criteria.
