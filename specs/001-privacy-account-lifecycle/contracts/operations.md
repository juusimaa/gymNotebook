## Retention schedule contract

The numerical limits below are draft product requirements, not verified provider guarantees or approved operational promises. Verify all sources and copies before approving or publishing them.

Use UTC instants for enforcement deadlines and explain them in the notice. A calendar day deadline is computed from the original event; copies, restoration, ledger state changes and retries cannot extend it. Schedule cleanup early enough to verify completion by the maximum.

| Category | Start event and maximum | Disposal/control |
| --- | --- | --- |
| Active account/notebook/acknowledgement | Until user removal or completed account deletion | Transactional deletion; no grace-period archive |
| Export buffers | Request lifetime; no persistent copies in selected design | Dispose readers/buffers on finish/abort/invalidation; any future spool requires ≤24h and immediate deletion cleanup |
| Identifying operational/security logs | Original collection +30 days maximum | Reviewed necessity/access restriction; no notebook content or credentials; erase/anonymize on account deletion unless continued retention is justified |
| Backups/PITR/snapshots/manual dumps | Deleted person's original deletion boundary +30 days maximum | Recovery-only access, finite provider windows, inventory and verified expiry of every source/copy |
| Live replicas/non-production account copies | Active deletion; retained recovery-only sources follow backup deadline | Remove active copies before success or avoid them; never keep a usable development notebook after deletion |
| Local deletion commit receipt | Purge on independent finalization, always before boundary +24h | Verified cleanup; all backup copies unusable before boundary +31d |
| Independent evidence including PREPARED | Original boundary/preparation +31 days maximum | Absolute expiry; proactively dispose objects/versions/snapshots and their copies; never restart on COMMITTED update |
| Rights-request correspondence/register | Reviewed purpose-specific maximum required before collection | Minimize personal content; record original absolute deadline and restricted disposal evidence; no invented indefinite default |

Example: a justified security log collected 20 days before deletion has at most 10 days left. Its retention is not reset. Non-justified log information must be removed/anonymized on deletion. Any exception beyond limits requires a reviewed specification/notice amendment with exact scope, obligation/claim, owner, review date, access restrictions and end condition; none is assumed.

The selected implementation avoids adding another non-atomic deletion store: do not collect identifying external logs without an approved continued-retention justification. Anonymize before collection or disable the collection instead. Clear incompatible existing logs before enabling this feature. If any non-justified identifying logs remain, deletion cannot report success until their removal/anonymization is verified; that requires a revised disposal protocol, not an assumption that asynchronous provider purge is atomic with PostgreSQL. This is a release gate for the whole deletion flow.

The Azure workspace declaration alone is insufficient: verify the strict 30-day purge setting, table-level and total retention, extra sinks and existing historical data. Track the original collection clock even where provider retention uses ingestion time. Delayed ingestion or retention-change grace periods must not extend the product deadline; use verified purge/minimization or block affected identifying collection. Apply durable configuration through IaC/supported deployment API and verify live results.

Independent storage cleanup must account for soft delete, versioning, replicas and diagnostics. An asynchronous lifecycle rule or application read denial is not evidence of destruction by the deadline. If provider capability cannot meet a limit, remove that processing/storage choice or obtain a reviewed specification change before rollout.

## Deletion/ledger protocol

**Unapproved candidate design.** The owner approved the restore safety outcome, not this two-store mechanism. Validate provider capabilities and every failure boundary, then demonstrate an isolated restore before seeking design approval. Do not implement this section as a settled architecture decision.

1. Validate bearer, throttle, take exclusive account transaction lock and freshly check identity/token/password and explicit confirmation. No receipt is created for cancellation/wrong password.
2. Capture a deletion boundary and absolute expiry. Durably create PREPARED in independent private storage with conditional/idempotent semantics. If this fails definitively, roll back and leave the notebook intact. An ambiguous storage timeout remains tracked until reconciled.
3. Delete the owned notebook/account in FK-safe order and write the local commit receipt in one PostgreSQL transaction. Verify affected ownership and commit. All writes/response chunks use the coordination protocol, so none can authorize new data after this commit.
4. Finalize COMMITTED independently using the database commit evidence. Only then report success. A crash after commit but before finalization leaves complete deletion plus PREPARED, not partial notebook erasure. Return an uncertain outcome if necessary; never claim rollback when commit is uncertain.
5. Reconcile outstanding prepared records promptly against authoritative live transaction evidence. Definitive rollback removes preparation; confirmed commit finalizes it. Unknown evidence blocks affected restore. Remove local receipts promptly, with an operational deadline ahead of 24 hours, and verify external disposal by day 31.

The protocol cannot atomically commit both stores. Test every crash boundary and lost acknowledgement. An external storage interface, if introduced, earns its abstraction only through the independently failing storage boundary and test requirements; do not add unrelated interfaces. Storage/identity library selection follows the existing dependency rule.

## Restore contract — fail closed

1. Isolate restoration from production ingress, background jobs, user credentials and application writers. Restore into a separate database/environment. Record source creation/original deadlines, schema version and covered time interval. Reject expired or incompatible pre-UUID sources before accessing user data.
2. Obtain the authoritative independent ledger, including unresolved preparations, completeness/integrity evidence and original expiries. A ledger loaded solely from the restored database is insufficient. Missing records, an unavailable ledger, incomplete coverage or ambiguous prepared outcomes keep ingress disabled. Successfully reading an empty list is not proof that no deletions occurred.
3. Resolve preparations only with authoritative transaction evidence; never use absence in an old backup as proof of rollback. Replay committed suppression by immutable UUID, with workouts/blocks/sets/exercises/acknowledgement/credentials removed. Apply log/copy expiry without resetting timestamps. Replays are idempotent.
4. Verify zero records for suppressed accounts and unchanged control accounts; verify foreign-key integrity and permitted retention. Rotate JWT signing credentials before reopening to invalidate pre-restore integer subject identities. Validate notice versions/configuration and migrations.
5. Record operator, date, source, coverage evidence, outcomes and authorization to reopen. Only enable ingress after all checks pass. A crash between any steps resumes in isolation and replays safely. Destroy or make unusable over-age sources before suppression evidence expires.

If authoritative transaction evidence is irrecoverably lost for a preparation, affected recovery remains unavailable. This is a deliberate availability tradeoff, not permission to guess which account was deleted or extend evidence indefinitely. Test ledger outage, corrupted/incomplete ledger, crash before/after DB commit, replay twice, reused username and day-30/day-31 boundaries.

## Rights handling

Provide a monitored contact for people unable to sign in and broader requests beyond the self-service file. Verify identity proportionately without automatically collecting identity documents. Track receipt and the one-calendar-month response deadline; verification must not silently restart it. Record permitted extension/refusal reasons and timely explanation. Use calendar-month arithmetic, including end-of-month cases, not a fixed 30-day timer. Do not expose secrets/security material automatically or reject a broader request solely because that material is excluded from the self-service export. Review the rights register's own data/retention before use.
