## Retention schedule contract

The numerical limits below are draft product requirements, not verified provider guarantees or approved operational promises. Verify all sources and copies before approving or publishing them.

Use UTC instants for enforcement deadlines and explain them in the notice. A calendar day deadline is computed from the original event; copies, restoration, restore steps and retries cannot extend it. Schedule cleanup early enough to verify completion by the maximum.

| Category | Start event and maximum | Disposal/control |
| --- | --- | --- |
| Active account/notebook/acknowledgement | Until user removal or completed account deletion | Transactional deletion; no grace-period archive |
| Export buffers | Request lifetime; no persistent copies in selected design | Dispose readers/buffers on finish/abort/invalidation; any future spool requires ≤24h and immediate deletion cleanup |
| Identifying operational/security logs | Original collection +30 days maximum | Reviewed necessity/access restriction; no notebook content or credentials; erase/anonymize on account deletion unless continued retention is justified |
| Backups/PITR/snapshots/manual dumps | Deleted person's original deletion boundary +30 days maximum | Recovery-only access, finite provider windows, inventory and verified expiry of every source/copy |
| Live replicas/non-production account copies | Active deletion; retained recovery-only sources follow backup deadline | Remove active copies before success or avoid them; never keep a usable development notebook after deletion |
| Deletion log lines (UUID, boundary, event) | Original collection +30 days maximum, as identifying logs | Needs the continued-retention justification (R6 Q2e); no username, notebook content or credentials |
| Preserved pre-restore branch | Created during a restore; deleted once reconciliation is verified, before reopening | Holds other users' live data and its own history; never kept as a standing backup |
| Rights-request correspondence/register | Reviewed purpose-specific maximum required before collection | Minimize personal content; record original absolute deadline and restricted disposal evidence; no invented indefinite default |

Example: a justified security log collected 20 days before deletion has at most 10 days left. Its retention is not reset. Non-justified log information must be removed/anonymized on deletion. Any exception beyond limits requires a reviewed specification/notice amendment with exact scope, obligation/claim, owner, review date, access restrictions and end condition; none is assumed.

The selected implementation avoids adding another non-atomic deletion store: do not collect identifying external logs without an approved continued-retention justification. Anonymize before collection or disable the collection instead. Clear incompatible existing logs before enabling this feature. If any non-justified identifying logs remain, deletion cannot report success until their removal/anonymization is verified; that requires a revised disposal protocol, not an assumption that asynchronous provider purge is atomic with PostgreSQL. This is a release gate for the whole deletion flow.

The Azure workspace declaration alone is insufficient: verify the strict 30-day purge setting, table-level and total retention, extra sinks and existing historical data. Track the original collection clock even where provider retention uses ingestion time. Delayed ingestion or retention-change grace periods must not extend the product deadline; use verified purge/minimization or block affected identifying collection. Apply durable configuration through IaC/supported deployment API and verify live results.

If independent storage is reintroduced (R6 option 3), its cleanup must account for soft delete, versioning, replicas and diagnostics. An asynchronous lifecycle rule or application read denial is not evidence of destruction by the deadline. If provider capability cannot meet a limit, remove that processing/storage choice or obtain a reviewed specification change before rollout.

## Deletion protocol

**Chosen direction, not yet proven.** Validate every failure boundary and demonstrate an isolated restore before seeking approval. See [research R6](../research.md#r6--independent-restore-evidence).

1. Validate bearer, throttle, take the exclusive account transaction lock and freshly check identity, token, password and explicit confirmation. Cancellation or a wrong password writes no log line.
2. Capture the deletion boundary. Log `deletion.intent` with the account UUID and boundary only.
3. Delete the owned notebook/account in FK-safe order in one PostgreSQL transaction. Verify affected ownership and commit. All writes/response chunks use the coordination protocol, so none can authorize new data after this commit.
4. Log `deletion.committed`, then report success. On definitive rollback, log `deletion.rolled_back` and leave the notebook intact. If the commit outcome is uncertain, return `deletion_outcome_unknown` and never claim rollback.

No second store exists, so there is nothing to finalize or reconcile after commit. A lost committed line is covered by the preserved-branch diff, and in the fallback by suspension (restore step 3).

## Restore contract — fail closed

1. **Isolate.** Disable API ingress and background writers before touching the database. Record the restore target `T`, schema version and covered interval. Reject targets before the UUID migration unless a reviewed compatible restore migration exists.
2. **Restore with preservation.** Run `neon branches restore main main@<T> --preserve-under-name <name>` so the pre-restore state survives as a separate branch.
3. **Reconcile.**
   - **Primary:** list PrivacyAccountId values present in the restored database and absent from the preserved branch. Delete those accounts again (workouts/blocks/sets, exercises, acknowledgement, credentials). Replays are idempotent.
   - **Fallback:** use this only if the preserved branch is unusable. First verify that log ingestion shows no gap from `T` to the restore; otherwise stay closed. Re-delete every UUID with a `deletion.committed` line after `T`. Ignore intents with a matching `deletion.rolled_back`. For an intent with neither, set SignInSuspendedAt by manual SQL, recorded in the restore log; never erase or revive it. Resolution follows [data-model.md → User additions](../data-model.md#user-additions).
   - **Credentials:** when the preserved branch is usable, copy `PasswordHash` and `TokenVersion` from it for surviving accounts whose values differ, so password changes after `T` are not reverted. In the fallback path this is impossible; record it in the restore log (research R5, P18).
   - Successfully reading an empty result is proof only when its source is verified. An unverified empty result keeps access closed.
4. **Verify.** Check zero records for re-deleted accounts, suspended accounts cannot sign in, control accounts are unchanged, and foreign keys and retention are intact. Rotate the JWT signing secret on every restore; this invalidates pre-restore integer subjects and revived revoked tokens (research R5, P18). Generate it directly into the Container Apps secret and never log or commit it. Validate notice versions/configuration and migrations.
5. **Reopen and clean up.** Record operator, date, target, evidence source, outcomes and authorization to reopen. Delete the preserved branch once verification passes, then enable ingress. A crash between steps resumes in isolation and replays safely.

If neither evidence source can be verified, recovery remains unavailable. This is a deliberate availability tradeoff, not permission to guess which account was deleted. Test preserved-branch diff, lost-database fallback, a log gap, intent-only suspension, rollback lines, replay twice, reused username and the Q2d invariant.

## Rights handling

Provide a monitored contact for people unable to sign in and broader requests beyond the self-service file. Verify identity proportionately without automatically collecting identity documents. Track receipt and the one-calendar-month response deadline; verification must not silently restart it. Record permitted extension/refusal reasons and timely explanation. Use calendar-month arithmetic, including end-of-month cases, not a fixed 30-day timer. Do not expose secrets/security material automatically or reject a broader request solely because that material is excluded from the self-service export. Review the rights register's own data/retention before use.
